# 编码回退与集成测试设计

## 目标
- 将未知编码的默认策略从强制 `gb18030` 改为保守处理。
- 为 `fetch` / `decodeToUTF8` 增加更贴近真实 HTTP 响应的集成测试。

## 方案比较
1. 未知编码继续默认 `gb18030`
   - 优点：中文站点偶尔更“看起来可读”
   - 缺点：会误解码非中文页面，污染标题、正文和指纹匹配
2. 未知编码默认 `utf-8`
   - 优点：简单
   - 缺点：依然是猜测，且会掩盖真实编码问题
3. 未知编码不强转，仅在明确声明或有限探测成功时转换（推荐）
   - 优点：更符合通用实践，降低误解码风险
   - 缺点：部分未知编码页面可能显示为原始字节内容

## 设计
- `detectEncoding` 对未知编码返回空字符串。
- `decodeToUTF8` 仅在存在明确编码时转换；若响应头未知，则仍允许 `meta` / `title` 分支提供编码线索。
- 新增 `fetch` 集成测试，验证：
  - `Content-Type: windows-1252` 时标题可被正确解码
  - 响应头未知但 `meta charset=windows-1252` 时正文可被正确解码
  - 响应头未知且无 `meta` / `title` 线索时不强转

## 风险控制
- 保持改动集中在 `pkg/encoding.go` 和测试文件。
- 先写失败测试，再做最小实现。
